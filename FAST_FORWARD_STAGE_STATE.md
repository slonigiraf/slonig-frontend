# Fast Forward stage-state architecture

There is **one authority for stage success**: the `Book.completedStages` list in IndexedDB. A UI busy flag, successful HTTP request, or Fast Forward run cursor is **not** a success checkpoint. Workers call `completeBookProcessingStage` (or the equivalent atomic book/stage helper) only after persisting their results.

A separate `Book.bypassedStages` list records **explicitly acknowledged unsuccessful stages**. Bypass does not imply success and never gets included in `getBookCompletedStages` or `isBookProcessingStageComplete`. `isBookProcessingStageSatisfied` is intended only for *prerequisite gating* where partial outputs can still be useful. Rerunning a stage clears its and downstream completion/bypass state; completing a bypassed stage removes its bypass marker.

`BookProcessingRun` checkpoints track the **execution** of a particular Fast Forward attempt. `completed` contains its confirmed successful stages, `failedStages` stores reasons by stable stage key, and `bypassedStages` records failures explicitly accepted for that run. The manager's next-stage cursor considers both successful and bypassed stages **settled**, but never counts a failure as successful. The UI displays a check for success, a warning for failure, and a bypass arrow for an acknowledged failure.

Command execution is tracked directly in the manager as well as through React progress. A command that starts and ends without a painted `busy=true` frame still gets its completion verified. When an in-flight stage stops, the manager checks the actual Book checkpoint before declaring that stage incomplete; this also reconciles UI snapshots that are one render behind IndexedDB. On failure Fast Forward stops without automatically waiving the failure. The **Skip** button to the left of Run in any stage price-confirmation popup records a bypass. When skipping the failed stage it also resumes Fast Forward from the next unsettled stage; if the failed stage actually has a persisted checkpoint, continuation reconciles it as success instead. Starting a fresh Fast Forward from a *later* stage also acknowledges the earlier recorded failure rather than inventing a success.

After a page reload, an interrupted running Fast Forward is restored as **paused**. The existing Fast Forward button is also its resume control: with user confirmation about potentially repeated provider charges, it calls `bookProcessingManager.resume` and preserves the original run cursor, completed stages, and models. It must not start a new run or reset downstream checkpoints. There is no separate toolbar Resume button.

The stage selector displays the entire pipeline, with prerequisite checks still applied to individual actions; it no longer locks navigation to the first incomplete stage. During Fast Forward its selected stage follows the manager's persisted cursor, and manual navigation remains independent. If a subsequent stage cannot operate on partial inputs, the run stops with an explicit unavailable-prerequisites message instead of spinning at the previous stage.

Regression coverage is in `bookProcessingManager.spec.ts`, `skipBookStage.spec.ts`, `bookStageNavigation.spec.ts`, and `bookStageBypass.spec.ts`. The Deduplicate concepts handoff is considered busy through generated review and database save, preventing premature missing-checkpoint failures. Additional syntax and mocked state-machine checks were performed without the full monorepo dependency tree.
